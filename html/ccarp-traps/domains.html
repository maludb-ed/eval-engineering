D1 · Solution Design & Architecture

17%

Video: EP02 ▶ 7:48 · EP03 ▶ 17:29

1.1 The pattern ladder

Augmented model (one model plus retrieval, tools and memory) → workflow (you draw the path in code; the model fills in the hard steps) → agent (the model picks its own steps at runtime). Each rung up buys flexibility and costs predictability, money and latency.

1.2 The rule

Use the simplest pattern that meets the requirement, and not one rung higher. The simplest rung is a legitimate pattern, not a failure to try hard enough. You can't tune your way out of the wrong pattern.

Traps: T9 gold plating (agent for a fixed task), T8 over-orchestration

1.3 Decomposition

Break a big, vague task into steps that each do one thing you can check. If one overloaded prompt gives inconsistent output, the exam usually wants decomposition, not a bigger model.

Traps: T1, T2 (step-by-step plus more tokens), an agent that "loops until done"

1.4 The four-part shape

Input → processing → output → feedback loop. A system without the last part can never improve. Expect stems where the feedback loop is quietly missing.

1.5 When multi-agent pays

There are two honest reasons to split: context isolation (each sub-agent sees only its slice) and parallel breadth (independent directions explored at once). Multi-agent runs cost about 15× the tokens of a chat, so the task has to be valuable enough to justify that.

Don't split when every agent needs the same context or each step depends on the one before. Contracts with cross-references and most coding work fall in this category.

Traps: split + a coordinator to patch the split (T7), caching a split you never needed (T10), T1

1.6 Business-value pillars

The guide names five: efficiency, transformation, productivity, cost, and a promised performance target. Name the pillar a design serves and what it costs on the others.

Trap: T12, serving the pillar someone said out loud instead of the one the constraint points to

60-second recap

  • Climb the ladder only as high as the constraint forces you.
  • Reproducible or auditable → workflow. Open-ended and genuinely hard → agent.
  • Split into multiple agents only for isolation or breadth, and name the token bill.
  • The least impressive option is often the right one.

D2 · Claude Models, Prompting & Context Engineering

13%

Video: EP04 ▶ 25:37

2.1 Model choice

Model choice trades capability against speed against cost, and your eval set decides it, not your gut. Either start cheap and move up, or start at the top and optimize down. Try adjusting settings such as effort before switching models.

Traps: T1 ("best model"), a router you don't need yet (T9), T2

2.2 Prompt design

Treat the system prompt as a stable template with slots to fill. Few-shot examples are the most reliable way to pin down format. Chain of thought isn't free: it adds latency, so use it only where it measurably helps.

Traps: T3 (a firmer line about format), T1, T2

2.3 Prompt caching

Put static content first (instructions, tools, policy) and dynamic content last. Cached reads cost about a tenth of the base input price and come back faster.

  • KIT If cache_read_input_tokens stays near zero, the prefix isn't byte-stable. A timestamp or reordered tools at the top will break it.
  • KIT Caching cuts cost and latency but frees no context-window space, so it doesn't fix context rot.

2.4 Skills and progressive disclosure

A Skill is a folder of instructions. Only its name and description load up front. The full instructions load when a task matches, and heavy files load later or never. That lets you offer a large library of expertise for almost no cost until it's used.

2.5 Context budget

More context isn't better context. Feed each step only what it needs through retrieval or Skills. KIT Load everything up front only when inputs are small and fixed; otherwise load just in time.

Traps: the biggest window with every document pasted in (T1), raising effort (T2), "tell it to ignore irrelevant content" (T3)

60-second recap

  • None of the correct answers here was "get the bigger thing".
  • Accuracy to spare and cost hurting → drop a tier, rerun the eval set.
  • Static first, cache on, dynamic last.
  • Examples pin format. Chain of thought only where it earns its latency.

D3 · Integration

19%Largest domain

Video: EP05 ▶ 33:53 · EP06 ▶ 44:45 · EP07 ▶ 56:07

3.1 Tool lists are permission lists

Each capability you give the agent is attack surface: an attacker who controls its input can use it. When a tool is too dangerous, remove it. Don't log around it or add a confirmation step. A bloated tool list also costs tokens on every request and makes the model more likely to pick the wrong tool.

Traps: logging (T5), a confirmation step (T9), T1. This is official sample 1.

3.2 Identity and authority gaps

An agent on a shared, all-seeing account will fetch data its user was never allowed to see. Make the agent act with the requesting user's identity so the system itself refuses what that user can't access.

Traps: "tell it to refuse sensitive questions" (T4), T5, T1

3.3 Direct API vs MCP vs agent-to-agent

  • Direct API/CLI fits one thing, once, from a system you already call, or a fixed integration where you own both sides. It's the cheapest option and gives the tightest control.
  • MCP fits many tools that change often or are shared across agents. It gives you a reusable tool surface with discovery.
  • A2A fits a sub-task that genuinely needs its own reasoning, context and tools. It has the highest coordination cost.

Don't use a protocol heavier than the integration needs.

KIT MCP auth: tokens should be audience-bound to the MCP server. Never pass client tokens through to upstream APIs; that's the confused-deputy problem.

Traps: an MCP server "for future tools" (T9), a finance agent for one number (T8), a general web tool (T11)

3.4 Progressive tool discovery

Let the model load tools on demand instead of listing every tool up front. It's least privilege applied to attention.

Traps: a bigger window (T1), merging servers (T7), a routing agent (T8)

3.5 RAG: chunking and index freshness

Chunk for coherence on the document's own boundaries (paragraph, clause, function). Fixed-size cuts split rules in half.

The index is a snapshot, so reindexing belongs in the pipeline and runs whenever the source changes. If you change the document embedding model but not the query one, retrieval quietly returns near misses.

Signature: confident, fluent and wrong right after a data change, with normal latency and an unchanged model. That points to the index. This is official sample 3.

3.6 Match retrieval to data shape and query

  • Prose → semantic search.
  • Structured records → query the database (filter, count, aggregate).
  • Code → symbols and call graph.
  • Lookup questions → narrow, precise retrieval. Synthesis questions → broad coverage.

Name the data shape and query pattern before choosing a strategy.

3.7 Contextual retrieval, or no retrieval

Prepend a short context sentence to each chunk when building the index. Used with both semantic and keyword (BM25) search, Anthropic reported roughly half as many failed retrievals.

A small, stable corpus of a few hundred pages can go straight into the prompt and be cached, with no pipeline. But a bigger window is a container, not a retrieval strategy.

3.8 Observability at scale

Four layers:

  • Traces: each request followed end to end.
  • Per-stage metrics: latency and quality for every stage.
  • Sampled judging: a sample of outputs scored against a rubric.
  • Cost meter: from the usage object on each response.

At scale, watch distributions and alert on drift, not on a single failure. Watch p95, not the average.

Latency levers: route simple traffic to a faster model, stream responses (users see text sooner), and move non-urgent work to batch.

Traps: more logging (T6), dropping verification (T6), a human on every response (T9), token/temperature knobs (T2)

60-second recap

  • The audit question is which tools exist and whose permissions they run with.
  • Use the simplest connection mechanism that meets the need.
  • Retrieval can be perfectly healthy and completely wrong at once. Check the index.
  • A logged request isn't a watched request.

D4 · Evaluation, Testing & Optimization

16%

Video: EP08 ▶ 1:07:04 · EP09 ▶ 1:15:10

4.1 The golden set

Real inputs paired with known-good answers, seeded from past failures. Curating it is the method. It turns "is the new version better?" into a number.

KIT Version it, and gate releases on no regression in any category, not only a better average.

4.2 Five metrics

Accuracy, latency, cost, safety and security. Safety and security are first-class metrics, each with its own cases and pass line.

4.3 Mixed grading

  • Code checks are cheap and never drift. Use them wherever right and wrong are clear.
  • A model judge handles fuzzy qualities like tone, but calibrate it against transcripts first.
  • Human reads confirm the other two are measuring what you think.

Using one grader for everything is the classic wrong answer.

4.4 Coverage

Include failures and adversarial inputs: typos, sarcasm, injection attempts. Test both where a behavior should happen and where it should not. KIT Also include irrelevant input, over-long input, and cases where experts disagree.

4.5 Baseline + A/B discipline

Record a baseline before you tune anything. Run both versions on the same golden set. Change one variable at a time, or you can't tell which change moved the score.

Traps: T6, T1, T2

4.6 The diagnosis tree

There are five suspects: prompt, context, retrieval, model, tooling. Read the symptom as evidence. If it tracks input length or how deep in the document the detail sits, suspect context and fix it by chunking, not by rewriting the prompt.

Trap: T7 wrong-layer fix

4.7 Cost order: outside in

Cache → route → batch. These don't change a word of the output, so you can apply them together and check the win on the bill. Batch runs about 50% cheaper. Only after that should you touch settings that affect quality (prompt wording, model tier, trimmed context), and then with an A/B test.

Trap: T10 premature optimization

60-second recap

  • Define what "correct" means before you argue about how to reach it.
  • The demo flatters. The golden set decides.
  • One change, one measurement.
  • Take the free wins first; touch quality-bearing settings last.

D5 · Governance, Safety & Risk Management

14%

Video: EP10 ▶ 1:26:51 · EP11 ▶ 1:38:47

5.1 Must vs should

Must → deterministic code. Should → a prompt is fine. A system prompt is guidance, not a guarantee. It shapes what the model probably does, never what it can't do.

5.2 Five failure modes

  • Hallucination: states something false with confidence.
  • Prompt injection: direct from the user, or indirect through content the model reads.
  • Tool misuse: a real tool called with the wrong arguments or at the wrong time.
  • Context poisoning: bad information treated as truth for the rest of the session.
  • Drift: slow degradation as the world changes.

Only hallucination is about the model on its own. The rest are about what the surrounding system lets it read and do.

5.3 Three guardrail layers

  • Input: screen requests, e.g. with a cheap, fast model.
  • Action: least privilege on tools.
  • Output: validate before the result reaches a user or system.

No single layer is enough. For hallucination: allow "I don't know", require quotes, and verify claims against the quotes.

5.4 Human-in-the-loop by risk tier

Sort actions by impact × reversibility. Low-stakes, reversible work (drafts) needs no human. Irreversible, high-stakes actions (moving money, regulator filings) get a human every time.

Traps: reviewing everything (T9), a "be careful" prompt (T4), self-rated confidence (T14)

5.5 Compliance starts with the data-flow map

Map where data is created, how it travels, where it rests, and who can touch it. Every arrow is somewhere a regulator will point. Each regulation is then a lens over the same map.

  • GDPR: residency (pin the inference and storage region), erasure, minimization. Minimization and erasure are still your job.
  • HIPAA: a signed BAA, HIPAA-ready access, encryption, access control and audit logging. Don't write raw PHI to logs. KIT SOC 2 is not HIPAA.
  • FedRAMP: authorizes the environment / boundary, not the model. Deploy inside an authorized path.

KIT These are obligations on the deployer. Never assume the vendor covers them.

5.6 Real controls vs theater

Real controls: zero data retention, signed agreements, region pinning, log redaction, and a human on consequential decisions. Proof comes from published audits (the trust portal), not from memos.

Traps: a privacy notice, a policy document, "encrypt and declare compliant" (T5)

5.7 Ethics as architecture

Bias testing is an eval spread across the groups you serve. Fairness means accuracy holds for each segment, not just on average. Transparency means telling users they're talking to an AI.

60-second recap

  • If a rule matters, make the architecture unable to break it.
  • Treat outside content as untrusted data, and limit what the model can do with it.
  • Put a human where a mistake is worst, not everywhere.
  • Draw the data flow before naming a control.

D6 · Stakeholder Communication & Lifecycle Management

14%

Video: EP12 ▶ 1:47:21

6.1 Discovery

Keep asking until the one deciding constraint shows up. It's usually cost or compliance, and it rules out most designs before you draw a box. Ask "what can never happen here?" "An agent that answers customer questions" is a feature, not a constraint.

6.2 A decision, not a diagram

A diagram shows what you'll build. A decision shows why. Say what the option buys, what it costs, and which pillar it serves, all in the sponsor's language rather than benchmark scores or model internals.

Traps: presenting the same pitch more forcefully (T3), adding components to impress (T9), rebuilding a correct design (T7)

6.3 SLAs for probabilistic systems

Promise a measured rate on a representative eval set, a p95 latency target, and an escalation path for misses. Never promise "always right."

Trap: T13 promising determinism

6.4 Handoff and lifecycle

The handoff should include:

  • the architecture, with the rationale for each major choice
  • the golden set and eval harness
  • known failure modes and what to watch for

The lifecycle is discovery → design → handoff → monitoring → iteration. KIT After launch, the system needs a named owner, drift alerts and an iteration cadence.

Trap: thinking the job ends at design

60-second recap

  • Find the constraint in discovery before drawing a box.
  • Bring a decision (buys / costs / pillar), not a wall of boxes.
  • Commit to a measured rate plus an escalation path.
  • Design the handoff so the system outlives you.

D7 · Developer Productivity & Operational Enablement

7%Smallest domain

Video: EP13 ▶ 1:58:17

7.1 Three config tiers

Personal: local to your machine and uncommitted. Team/project: checked into the repository. Managed: org policy pushed to every machine, which no one below can switch off. Put each decision on the right shelf.

7.2 Guidance vs enforcement

The instructions/memory file (e.g. CLAUDE.md) is guidance. Permission rules and hooks in settings are enforcement. "Never touch production" in the instructions file is a note, not a wall.

7.3 Precedence

Deny beats allow. Rules from different scopes merge rather than replace each other. A managed rule can't be loosened by personal or team settings, which is why real guardrails live there.

7.4 What belongs in the shared file

Build and test commands, project layout and conventions: anything a teammate would otherwise have to be told. Personal shortcuts and private sandbox links stay out of the repository.

Traps: cramming everything into one file, per-engineer copies (T15), copying a senior engineer's personal setup

7.5 Operational use

The coding agent can read logs, trace errors and draft fixes, with least privilege: read, diagnose, propose, then ship through the normal deploy path.

Traps: prod write access "for speed" (T11), a "be careful" note (T4), log-and-review afterwards (T5), turning permissions off and relying on code review

60-second recap

  • Must hold → a settings rule or hook. Should → the instructions file.
  • Guarantees go in the managed layer.
  • It's 7% of the exam. Learn it cleanly, then study a heavier domain.
