How items are framed

The six exam scenarios

Foundations questions sit inside recurring production scenarios, and each sitting draws four of the six officially published ones at random. Know each setting well enough that you only need to read the part of the stem that changes.

Three builds, three not

Scenarios 1, 3 and 4 are things you build with the Agent SDK. Scenarios 2 and 5 drop Claude Code into a repository, and 6 is a document pipeline. A draw of four always crosses that line, so you can't prepare only one half.

The small domain you can't dodge

D5 Context & Reliability is only 15% of the weight, but it's a primary domain in four of six scenarios, so at least two of your four will lean on it. D4 is named in only two.

The scenario names who the answer is for

Same four options, different consumer: if a person reads the output, explicit criteria plus examples fix vague content. If a service parses it, only a schema makes the shape certain.

Scenario 1 · domains D1, D2, D5

Customer Support Resolution Agent

Agent SDK support agent with MCP tools get_customer, lookup_order, process_refund, escalate_to_human; target of 80%+ first-contact resolution.

Architect question it asks most: What can it touch? · 3 official sample questions in the guide

What it tests

  • Refund limits and identity checks enforced by hooks and prerequisite gates, not prompts.
  • Escalation triggers: an explicit request, a policy gap, or no progress. Not sentiment.
  • Structured handoff to the human; a case-facts block for IDs and amounts.
  • Business-rule errors are non-retryable; an empty lookup isn't an error.

Scenario 2 · domains D3, D5

Code Generation with Claude Code

A team development workflow: slash commands, CLAUDE.md, plan mode vs direct execution.

Architect question it asks most: What can it touch? · 3 official sample questions in the guide

What it tests

  • Team conventions and commands live in the repo, not in ~/.claude.
  • Stated scope (dozens of files) → plan mode from the start.
  • Path-scoped rules for file types spread across directories.
  • Long sessions degrade: /compact, subagents, or a fresh session seeded with a summary.

Scenario 3 · domains D1, D2, D5

Multi-Agent Research System

A coordinator delegating to search / analyze / synthesize / report subagents that produce cited reports.

Architect question it asks most: Where does the work run? · 3 official sample questions in the guide

What it tests

  • Hub and spoke; subagents only know what the Task prompt passes them.
  • Coverage holes with every subagent succeeding → a decomposition problem.
  • Structured claim–source mappings with dates; report conflicts, don't resolve them silently.
  • Retry only the failed subagent; proceed with partials and annotate gaps.

Traps it leans on

T7 Assumed shared memoryT10 Lossy handoffT14 Blind or blanket retryT15 Error conflation

Scenario 4 · domains D2, D3, D1

Developer Productivity with Claude

Agent SDK tooling over built-in tools (Read, Write, Edit, Bash, Grep, Glob) plus MCP servers; legacy-codebase work.

Architect question it asks most: What can it touch? · no official samples, so you're least likely to have seen its item shapes

What it tests

  • Grep for contents, Glob for names; explore incrementally, don't read everything.
  • Edit uses unique text; fall back to Read + Write.
  • Adaptive decomposition for open-ended legacy investigation.
  • Scoped tools per role; community MCP servers before custom ones.

Scenario 5 · domains D3, D4

Claude Code for Continuous Integration

Automated code review, test generation and PR feedback; actionable findings with minimal false positives.

Architect question it asks most: Where does the work run? (every published sample) · 3 official sample questions in the guide

What it tests

  • -p for non-interactive runs; --output-format json + --json-schema.
  • A fresh reviewer instance, never the session that wrote the code.
  • Explicit categorical criteria to cut false positives, not “be conservative”.
  • Include prior findings so re-reviews report only new issues.

Scenario 6 · domains D4, D5

Structured Data Extraction

Unstructured documents → JSON-schema-validated output; edge cases and downstream integration.

Architect question it asks most: How is intent carried? · no official samples, so you're least likely to have seen its item shapes

What it tests

  • Tool use + a JSON schema; nullable fields to avoid fabrication.
  • Validation-feedback retries; stop when the data isn't in the source.
  • Batch for latency-tolerant volume, keyed by custom_id.
  • Validate by document type; stratified sampling; field-level calibrated confidence.

Traps it leans on

T6 False assuranceT14 Blind or blanket retryT4 Knob, not designT5 Unreliable proxy
