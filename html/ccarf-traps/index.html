Claude Certified Architect – Foundations · CCAR-F

Advice can't promise “never”. Only a mechanism can.

Foundations items describe a real production system, then offer four options that all sound sensible. Usually three of them are the same wrong answer in different clothes. These notes teach you to spot those wrong answers by shape and pick the mechanism the stem is asking for.

Tool 1: every item asks one of four design questions

Name which question you're in, and options that answer a different question drop off the page.

≈16 items · D1

Where does the work run?

One loop, a coordinator with subagents, or a headless CI run.

≈23 items · D2 + D3

What can it touch?

Tools, MCP servers, configuration, permissions: what it's allowed to do.

≈12 items · D4

How is intent carried?

Prompt structure, examples, schemas, and validation before anything downstream trusts the output.

≈9 items · D5

What survives?

What the system still knows an hour in, after a crash, and when it doesn't know.

Tool 2: sort every option into two piles

Guidance: asks

  • A line in CLAUDE.md or another instruction file
  • A sentence in the system prompt, however firmly it's worded
  • Few-shot examples of the rule
  • A README note, a PR template, a team convention

Guarantee: stops

  • A hook that blocks or rewrites the tool call
  • A prerequisite gate or permission rule that denies it
  • A schema the output must satisfy (tool use + JSON schema)
  • A forced tool_choice, or allowed-tools frontmatter

When the stem says must, never, always or cannot, every guidance option is a distractor.

The difference isn't how strongly the words are written. It's whether anything actually stops when the words get ignored. A consequence can act as the absolute too: money moving to the wrong account is a claim about every future case, even when the stem never says “never”.

The three reads, in order

  1. Read the last sentence of the stem first

    “Most effective first step”, “most likely root cause” and “most maintainable” are different questions, and the same system has a different right answer for each. Also check how many responses it wants.

  2. Name the design question, then look for an absolute

    If there's a must / never / always / cannot, it kills every option that only tells the system something. Only a mechanism in the path survives.

  3. No absolute? The stem already named the cause

    That's most items. Answer that cause at the size the evidence justifies. The cheap fix at the root beats extra machinery, and good engineering that answers a different question still loses.

Method adapted from Vivek Amilkanthawar's CCAR-F Full Course (EP01, EP12, EP15).
