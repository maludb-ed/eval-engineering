1.1 Agentic Loops

Task statement: Design and implement agentic loops for autonomous task execution

S1 Customer Support Resolution AgentS3 Multi-Agent Research SystemS4 Developer Productivity with Claude
Key facts
  • Loop lifecycle: send request → inspect stop_reason → execute requested tools → return results into the conversation → repeat.
  • stop_reason: "tool_use" means the model is requesting tool execution; stop_reason: "end_turn" means the model is finished and the loop should exit.
  • Tool results must be appended to the conversation history so the model can reason about its next action; the model is stateless between API calls.
  • If you skip the inspect step, the agent goes silent after one tool call; if you skip the append step, the model never sees the result and retries the same tool.
  • The next action is chosen by model-driven decision-making over the accumulated context, not by pre-configured decision trees or hardcoded routes.
  • The model can emit conversational text alongside a tool_use stop reason — the presence of assistant text is never a completion signal.
  • A hard iteration cap is acceptable only as a fail-safe against runaway loops; it must never be the primary stop mechanism.
  • Official anti-patterns: parsing natural-language phrases ("I'm done", "task complete") for termination; arbitrary iteration caps as the primary stop; checking assistant text as a completion indicator.

Exam traps

  • Any option that terminates the loop by regex/string-matching the assistant's text ("task complete") is wrong — the model may say "finished step one, moving to step two" and the loop breaks mid-task.
  • "Stop after N iterations" offered as the loop's control mechanism is wrong; end_turn drives control flow, caps are only a safety net.
  • Options where a decision tree or hardcoded route determines the next tool call are wrong — the correct answer is that tool results enter the conversation and the model reasons about what to do next.
  • Code-snippet questions with one loop step missing: name the dropped step (inspect stop_reason, execute the tool, or append the result) rather than a plausible-sounding unrelated fix.

1.2 Multi-Agent Orchestration

Task statement: Orchestrate multi-agent systems with coordinator-subagent patterns

S1 Customer Support Resolution AgentS3 Multi-Agent Research System
Key facts
  • Hub-and-spoke topology: the coordinator manages all inter-subagent communication, error handling, and routing; subagents do not communicate peer-to-peer.
  • Subagents have isolated context — they do not inherit the coordinator's conversation history.
  • Coordinator responsibilities: task decomposition, delegation, result aggregation, and dynamic subagent selection based on query complexity.
  • Iterative refinement loop: evaluate the synthesized result for gaps, re-delegate targeted subtasks, re-synthesize until coverage is sufficient.
  • Overly narrow task decomposition is the signature risk: every subagent succeeds individually while the aggregate output has incomplete coverage.
  • Routing all subagent communication through the coordinator provides observability and a single point of error handling.
  • Context isolation prevents attention dilution — a subagent doing one focused job is not distracted by dozens of turns of unrelated coordinator history.
  • When one subagent fails mid-workflow, retry only the failed subagent; successful siblings may already have committed side effects.

Exam traps

  • Options letting subagents message each other directly are wrong — in the tested coordinator-subagent pattern, everything routes through the hub.
  • "The subagents underperformed" as the diagnosis when every subagent reported success but coverage is incomplete — the correct root cause is the coordinator's overly narrow decomposition.
  • Blanket retry of all subagents after one failure — wrong because completed subagents may have side effects; the graded answer is a targeted retry of only the failed one.
  • Assuming a subagent can see the coordinator's earlier conversation "because it was spawned from it" — context is isolated and only explicitly passed information is available.

1.3 Subagent Invocation & Context Passing

Task statement: Configure subagent invocation, context passing, and spawning

S3 Multi-Agent Research SystemS4 Developer Productivity with Claude
Key facts
  • Subagents are spawned via the Task tool; the coordinator's allowedTools must include "Task" or delegation is impossible.
  • Subagent context must be explicitly passed in the invocation prompt — there is no automatic inheritance of coordinator history and no shared memory.
  • AgentDefinition configures each subagent type: description, system prompt, and per-subagent tool restrictions.
  • Parallel subagents are spawned by issuing multiple Task tool calls in a single coordinator response.
  • Coordinator delegation prompts should specify goals plus quality criteria, not step-by-step procedures.
  • Use structured data formats that separate content from metadata (source URLs, document names, page numbers) so attribution survives multi-agent hand-offs.
  • Fork-based session management lets you explore divergent approaches from a shared, already-computed baseline instead of recomputing it per branch.

Exam traps

  • "Coordinator can't delegate" scenarios where the answer is a missing "Task" entry in allowedTools — distractors point at prompts, model choice, or subagent definitions.
  • Options assuming a subagent automatically sees the coordinator's conversation or a shared memory store — all context transfer is explicit via the prompt.
  • Delegation prompts written as rigid step-by-step procedures presented as best practice — the graded answer specifies goals and quality criteria.
  • Passing findings between agents as unstructured prose when citations must survive — the correct pattern separates content from source metadata in a structured format.

1.4 Workflow Enforcement & Handoffs

Task statement: Implement multi-step workflows with enforcement and handoff patterns

S1 Customer Support Resolution Agent
Key facts
  • Programmatic enforcement (hooks, prerequisite gates) provides deterministic compliance; prompt-based guidance is probabilistic with a non-zero failure rate.
  • Rules that must never break — identity verification before financial operations, compliance boundaries — belong in code, not in the prompt.
  • Prerequisite gates block downstream tool calls until required steps complete, e.g., block process_refund until get_customer has verified the customer.
  • Prompts remain appropriate for preferences: style, tone, and formatting, where occasional deviation causes no real harm.
  • Structured handoff protocols for escalation carry customer details, root cause, and recommended actions so a human can act without transcript access.
  • A complete handoff summary includes concrete fields such as customer ID, root cause, refund amount, and a recommendation.
  • Multi-concern requests should be decomposed, investigated in parallel where independent, and synthesized into one unified resolution.

Exam traps

  • "Strengthen the prompt" (firmer wording, all-caps, more examples) offered where the scenario demands guaranteed compliance — the graded answer is a hook or prerequisite gate.
  • Escalation options that hand the human a raw transcript, or nothing at all, instead of a structured summary with customer ID, root cause, and recommended action.
  • Workflows that answer only the first issue in a multi-issue message, or return disjointed per-issue replies instead of a synthesized unified resolution.
  • Treating "works in 99% of test runs" as sufficient for a financial or security rule — non-zero failure rates are the stated reason prompts alone fail this requirement.

1.5 Agent SDK Hooks

Task statement: Apply Agent SDK hooks for tool call interception and data normalization

S1 Customer Support Resolution Agent
Key facts
  • Hooks provide deterministic guarantees; prompts provide only probabilistic compliance — the central distinction this task statement tests.
  • Interception hooks run before a tool call executes and can block or redirect it to enforce compliance rules.
  • Canonical interception example: block any refund over $500 and redirect to human escalation, guaranteed regardless of the prompt.
  • PostToolUse hooks transform or normalize tool results before the model sees them.
  • Canonical normalization example: reconciling Unix timestamps, ISO 8601 dates, and numeric status codes from different backends into one consistent format.
  • Normalizing in a hook uses cheap deterministic code instead of model reasoning, saving tokens and preventing conversion errors.
  • Rule of thumb: "guaranteed / required / must never happen" → hook; "preferred / usually / stylistic" → prompt.

Exam traps

  • When the stem says compliance must be guaranteed, distractors offer stronger prompt wording, few-shot examples, or confidence thresholds — all probabilistic; the answer is a hook.
  • Options that normalize inconsistent data formats via prompt instructions ("always convert dates to ISO 8601") instead of a PostToolUse hook — probabilistic and token-wasteful.
  • Confusing hook timing: interception/blocking happens before tool execution; result transformation happens in PostToolUse after the tool returns.
  • Believing a 99%-reliable prompt can be tuned to 100% — the exam treats any non-zero failure rate as unacceptable for financial or security rules.

1.6 Task Decomposition Strategies

Task statement: Design task decomposition strategies for complex workflows

S3 Multi-Agent Research SystemS4 Developer Productivity with Claude
Key facts
  • Two tested strategies: fixed sequential pipelines (prompt chaining) versus dynamic adaptive decomposition.
  • Prompt chaining hard-codes a known step sequence, guaranteeing every step runs in order and nothing is skipped.
  • Canonical prompt-chaining example: analyze each file individually, then a separate cross-file integration pass.
  • Dynamic adaptive decomposition generates new subtasks from what each step discovers, building the plan as it goes.
  • Canonical adaptive example: open-ended investigation such as hunting hidden dependencies in a legacy codebase.
  • Selection rule: prompt chaining for predictable multi-aspect reviews; dynamic decomposition for open-ended investigation.
  • Decomposition quality drives outcome quality — subtasks scoped too narrowly produce incomplete coverage even when every subtask succeeds.

Exam traps

  • Picking dynamic adaptive decomposition for a workflow whose steps are fully known in advance — over-engineering; the graded answer is the fixed pipeline that guarantees sequence.
  • Picking a fixed pipeline for genuinely open-ended investigation — the script can't anticipate what discovery will surface; the graded answer is adaptive decomposition.
  • Single-prompt "do the whole review at once" options where the tested pattern is per-file passes plus a distinct integration pass.
  • Blaming execution when coverage is incomplete — if every subtask succeeded but the result has holes, the decomposition itself was scoped wrong.

1.7 Session State, Resumption & Forking

Task statement: Manage session state, resumption, and forking

S3 Multi-Agent Research SystemS4 Developer Productivity with Claude
Key facts
  • Sessions persist state — conversation history, tool results, findings — and can be resumed rather than rebuilt.
  • Resumption uses --resume <session-name> and is appropriate when prior context remains mostly valid.
  • When resuming after changes, explicitly identify what changed so the agent performs targeted re-analysis instead of trusting stale results.
  • fork_session branches divergent explorations from a shared baseline, so expensive shared analysis is computed once and inherited by every branch.
  • Forked branches are independent — exploring alternative approaches in parallel without cross-contamination or re-computing the baseline.
  • Stale tool results are the key hazard of resumption: old file reads and schemas make the agent reason confidently about a reality that no longer exists.
  • When prior tool results are largely stale, prefer a fresh session seeded with a structured summary of prior findings over resuming the old session.

Exam traps

  • Resuming a session whose tool results are stale because "the context is valuable" — the graded answer is a fresh session seeded with a structured summary of the findings.
  • Re-running the expensive shared analysis for each alternative approach instead of computing it once and using fork_session to branch.
  • Treating fork and resume as interchangeable: resume continues one timeline; fork creates divergent branches from a shared baseline.
  • Assuming a resumed agent automatically detects that the environment changed — stale results are trusted unless you explicitly direct re-analysis or start fresh.

60-second recap

  • The loop is plumbing: inspect stop_reason, execute, append, repeat. Exit on end_turn.
  • Hub and spoke: subagents get only what you pass them; retry only the one that failed.
  • Guaranteed rules → hooks and gates. Preferences → prompts.
  • Known steps → pipeline; open-ended discovery → adaptive decomposition.
  • Resume continues, fork branches, and a fresh session plus a summary beats stale context.

2.1 Tool Descriptions & Interface Boundaries

Task statement: Design effective tool interfaces with clear descriptions and boundaries

S1 Customer Support Resolution AgentS3 Multi-Agent Research SystemS4 Developer Productivity with Claude
Key facts
  • Tool descriptions are the primary mechanism the model uses for tool selection; minimal descriptions lead to unreliable selection.
  • Good descriptions include input formats, example queries, edge cases, and explicit boundary statements distinguishing the tool from similar alternatives.
  • Ambiguous or overlapping descriptions (and near-identical names) cause misrouting between tools that cover similar ground.
  • The first-step fix for tool confusion is expanding each tool's description — a low-effort, root-cause remedy.
  • Renaming tools to eliminate functional overlap is the next escalation when enriched descriptions are not enough.
  • Generic multi-purpose tools should be split into purpose-specific tools with defined contracts.
  • System prompt wording affects tool selection: keyword-sensitive instructions can override well-written descriptions, so review prompts and descriptions together.
  • A useful description template: what the tool does, when to use it over its siblings, an example invocation with realistic arguments, and the error conditions it can return.

Exam traps

  • Adding few-shot examples or building a routing classifier to fix tool confusion — both are over-engineered distractors; the root-cause fix is better descriptions.
  • Assuming the model uses anything beyond name, description, and input schema to choose a tool — there is no other selection signal.
  • Fixing only the tool descriptions while ignoring a system prompt whose keywords steer the agent toward the wrong tool.
  • Jumping straight to splitting or renaming tools when the question asks for the best first step — description enrichment comes before structural changes.

2.2 Structured Error Responses for MCP Tools

Task statement: Implement structured error responses for MCP tools

S1 Customer Support Resolution AgentS3 Multi-Agent Research System
Key facts
  • MCP communicates tool failure to the agent via the isError flag pattern on tool results.
  • Structured error metadata should include an errorCategory, an isRetryable boolean, and a human-readable description.
  • Four error classes: transient (retryable), validation (fix the input), business (not retryable), permission (escalate).
  • Business rule violations should return a retriable: false flag plus a customer-friendly explanation, so the agent explains the policy rather than looping.
  • Uniform, undifferentiated error responses prevent the agent from making appropriate recovery decisions.
  • Subagents should recover locally from transient failures rather than escalating every timeout to the coordinator.
  • A malformed request (tool never ran) is a JSON-RPC protocol error; a post-invocation external failure (404, 503) is a tool result with is_error: true.
  • Zero results from a successful query is a valid empty result, not an access failure — the two must be reported distinguishably.

Exam traps

  • Options that return plain-text or generic error messages ("operation failed") — they hide the retry/abandon/escalate signal and cause wasted retry turns.
  • Treating a business error as retryable: the agent wastes multiple turns retrying a policy violation that can never succeed; the graded fix is retriable: false with an explanation.
  • Reporting a malformed request as an is_error tool result (or a downstream 404/503 as a protocol error) — the JSON-RPC vs. tool-result boundary is whether the tool actually executed.
  • Flagging an empty search result as an error (causes endless retries) or, inversely, marking an access failure as a successful empty result (causes silent data gaps).

2.3 Tool Distribution & tool_choice

Task statement: Distribute tools appropriately across agents and configure tool choice

S1 Customer Support Resolution AgentS3 Multi-Agent Research System
Key facts
  • Giving an agent too many tools (e.g., 18 instead of a focused 4–5) degrades tool selection reliability.
  • Agents holding tools outside their specialization tend to misuse them (attention drift into out-of-role work).
  • Scoped tool access is least privilege applied to tools: restrict each subagent's tool set to what its role needs.
  • Replace generic tools with constrained, purpose-specific alternatives rather than sharing one broad tool everywhere.
  • For high-frequency cross-role needs, provide a narrow scoped tool (e.g., a scoped verify_fact for a synthesis agent) and route the complex remainder through the coordinator.
  • tool_choice: "auto" — tool use optional; the model may return plain text.
  • tool_choice: "any" — the model must call some tool from the list; guarantees a tool call in pipelines.
  • Forced tool selection (naming a specific tool) guarantees that exact tool is called — used to ensure a prerequisite step runs first, then switch to "auto".
  • Business rules should be enforced in tool code, not in prompt instructions — structural fixes beat prompt fixes.

Exam traps

  • "Give the subagent the full tool set so it never gets blocked" — wrong; broad access degrades selection and invites misuse. Scoped tools plus coordinator delegation is the graded pattern.
  • Relying on tool_choice: "auto" when the scenario requires a guaranteed tool call — "auto" permits a plain-text reply; use "any" or forced selection.
  • Enforcing a required tool ordering through system-prompt instructions instead of forcing the first tool via tool_choice — prompt wording cannot guarantee sequencing.
  • Routing every small verification through the coordinator when the stem describes a high-frequency, mostly-simple need — the scoped cross-role tool is the intended answer.

2.4 MCP Server Integration & Configuration

Task statement: Integrate MCP servers into Claude Code and agent workflows

S1 Customer Support Resolution AgentS4 Developer Productivity with Claude
Key facts
  • Project-scoped MCP servers go in .mcp.json in the repository — shared with the team via version control; right for shared tooling.
  • User-scoped MCP servers go in ~/.claude.json — personal or experimental servers not forced on teammates.
  • .mcp.json supports environment variable expansion (e.g., ${GITHUB_TOKEN}) so credentials stay local; secrets are never committed.
  • Tools from all configured MCP servers are discovered at connection time.
  • Detailed MCP tool descriptions (capabilities and outputs) should be enhanced just like native tool descriptions — they drive selection.
  • MCP resources expose content catalogs (issue lists, directory trees, schemas), reducing blind exploratory tool calls.
  • Prefer existing community MCP servers over custom implementations for standard integrations; build custom only for team-specific needs.
  • stdio transport is the default for a server on the same machine (no network, no auth overhead); SSE is for servers that must run on a remote host.

Exam traps

  • Putting a team-shared server in ~/.claude.json — it never reaches version control, so teammates lack it; shared tooling belongs in project-scoped .mcp.json.
  • Hardcoding an API key or password into a committed .mcp.json — the graded answer uses environment variable expansion.
  • Choosing SSE transport for a server running on the same machine as the client — stdio is correct; SSE adds latency and authentication design for no benefit.
  • Writing a custom MCP server for a standard integration (e.g., a mainstream issue tracker) when a community server exists — buy before build.

2.5 Built-in Tools (Read, Write, Edit, Bash, Grep, Glob)

Task statement: Select and apply built-in tools (Read, Write, Edit, Bash, Grep, Glob) effectively

S4 Developer Productivity with Claude
Key facts
  • Grep searches file contents for patterns — function names, error messages, call sites; Glob matches file paths by name or extension pattern.
  • Mnemonic: Grep is for contents, Glob is for names.
  • Glob works on paths without reading file contents, making it fast and token-efficient for scoping work by file type.
  • Read loads full file contents into context; Write overwrites an entire file.
  • Edit performs targeted modifications via unique text matching — not line numbers, because models miscount lines over large contexts and unique strings are immune to line-number drift.
  • Edit fails when the anchor text is not unique in the file; the fallback is Read the full file plus Write the complete modified file.
  • Build codebase understanding incrementally: start with Grep to find entry points, then Read selectively following imports — do not read all files upfront.
  • Tracing a function's usage across wrapper modules is a Grep job (content search across the codebase).

Exam traps

  • Answers that use Glob to search inside files or Grep to find files by extension — swapped roles are the standard distractor pair.
  • "Read every file in the module first, then analyze" — exhausts context; the graded strategy is Grep-first incremental exploration.
  • Expecting Edit to target changes by line number, or treating a failed Edit (non-unique match) as a dead end instead of falling back to Read + Write.

60-second recap

  • Descriptions are the selection signal, so enrich them first.
  • Errors are structured: category, retryable flag, and empty ≠ error.
  • Four or five scoped tools per role; tool_choice when a call must happen.
  • Team servers in .mcp.json with env-var secrets; stdio when local.
  • Grep for contents, Glob for names; Edit by unique text.

3.1 CLAUDE.md Hierarchy

Task statement: Configure CLAUDE.md files with appropriate hierarchy, scoping, and modular organization

S2 Code Generation with Claude CodeS5 Claude Code for Continuous Integration
Key facts
  • The hierarchy has three levels: user (~/.claude/CLAUDE.md), project (root CLAUDE.md or .claude/CLAUDE.md), and directory-level files scoped to a subfolder.
  • User-level settings apply only to that user; instructions in ~/.claude/CLAUDE.md are not shared with teammates because they never enter version control.
  • Project-level CLAUDE.md is committed to the repo and ships with every clone — the correct home for team-wide conventions.
  • Diagnostic pattern: a rule that works for one developer but not teammates is trapped in a user-level file; move it to project level.
  • The @import syntax references external files from CLAUDE.md, keeping the root file modular instead of monolithic.
  • The .claude/rules/ directory organizes topic-specific rule files (e.g., database conventions, API security) split out of a large CLAUDE.md.
  • The /memory command verifies which memory files are currently loaded — the first step when diagnosing configuration drift.
  • CLAUDE.md content is injected automatically at session start, so an oversized monolithic file costs tokens on every session.

Exam traps

  • Any option that fixes "teammates don't get the standards" by rewording the rule or strengthening the prompt is wrong — the root cause is placement (user level vs project level), not phrasing.
  • Putting team-shared configuration in the home-directory file is the classic wrong answer; it can never reach version control.
  • Options that keep everything in one giant always-loaded CLAUDE.md (treating it as a knowledge base) lose to @import plus focused .claude/rules/ files.
  • Guessing at which instructions are active instead of running /memory — the exam rewards verifying loaded memory files over speculation.

3.2 Slash Commands & Skills

Task statement: Create and configure custom slash commands and skills

S2 Code Generation with Claude CodeS4 Developer Productivity with Claude
Key facts
  • Project-scoped commands live in .claude/commands/ and are shared through version control; user-scoped commands live in ~/.claude/commands/ and stay personal.
  • "The whole team needs a /review command on clone" → create it in .claude/commands/ in the project repository.
  • Skills live in .claude/skills/ as folders with SKILL.md files configured via YAML frontmatter.

  • Decision rule: CLAUDE.md holds always-loaded universal standards; skills hold on-demand workflows.
  • Developers can create personal variants of team skills to customize shared workflows.

Exam traps

  • Placing a team command in the home-directory commands folder — it never reaches teammates; project .claude/commands/ is the shared location.
  • Stuffing an occasional workflow into CLAUDE.md (always loaded, tokens on every session) when an on-demand skill is the right container.
  • Handling a skill's verbose output with prompt instructions ("be concise") instead of the structural fix, context: fork.
  • Trusting a prompt to keep a review skill from writing files instead of restricting it with allowed-tools — the frontmatter guarantee beats the instruction.

3.3 Path-Specific Rules

Task statement: Apply path-specific rules for conditional convention loading

S2 Code Generation with Claude CodeS4 Developer Productivity with Claude
Key facts
  • .claude/rules/ files support YAML frontmatter paths fields containing glob patterns that control when the rule file activates.
  • Path-scoped rules load only when Claude edits files matching the glob, reducing irrelevant context in every other session.
  • Glob-pattern rules beat directory-level CLAUDE.md files when file types are spread across directories — e.g., test files living alongside code throughout the repo.
  • A single rule file with a pattern like **/*.test.py covers matching files everywhere, with no per-directory duplication.
  • Canonical scenario: distinct conventions for React components, API handlers, and DB models with tests spread throughout → rule files with frontmatter glob patterns.
  • Conditional loading saves tokens and prevents cross-contamination, such as styling conventions being applied to database scripts.
  • Decision rule: CLAUDE.md = universal standards, skills = on-demand workflows, path rules = file-type conventions scattered across the codebase.

Exam traps

  • Choosing per-directory CLAUDE.md files for conventions keyed to file type — when tests or components are spread across many directories, that means duplication; glob-based path rules are the graded answer.
  • Dumping all file-type conventions into the root CLAUDE.md so they load on every session — path rules exist precisely to avoid this always-loaded cost.
  • Confusing scoping mechanisms: directory-level CLAUDE.md scopes by location, paths frontmatter scopes by pattern; questions hinge on which dimension the scenario describes.

3.4 Plan Mode vs Direct Execution

Task statement: Determine when to use plan mode vs direct execution

S2 Code Generation with Claude CodeS4 Developer Productivity with Claude
Key facts
  • Plan mode targets complex tasks: large-scale changes, multiple valid approaches, and architectural decisions.
  • Direct execution suits simple, well-scoped changes — the official example is adding a single validation check.
  • Plan mode enables safe codebase exploration and design before committing to any changes.
  • The Explore sub-agent isolates verbose discovery output during investigation, returning only concise summaries to the main context.
  • Canonical scenario: monolith-to-microservices restructuring touching dozens of files → enter plan mode to explore, map dependencies, and design first.
  • The modes combine: plan mode for investigation and design approval, then direct execution for implementation.
  • Selection signals live in the scenario text: stated file counts, architectural scope, and ambiguity all point to plan mode; a clear, contained fix points to direct execution.

Exam traps

  • "Start with direct execution and switch to plan mode if it gets hard" is wrong when the scenario already states the complexity — dozens of files or service boundaries mean plan mode from the start.
  • Over-planning in the other direction: forcing plan mode onto a trivial single-file fix wastes effort; well-scoped changes execute directly.
  • Letting verbose exploration flood the main session instead of delegating discovery to the Explore sub-agent.
  • Treating plan mode and direct execution as mutually exclusive for a whole task — the graded pattern often plans the investigation, then implements directly after approval.

3.5 Iterative Refinement

Task statement: Apply iterative refinement techniques for progressive improvement

S2 Code Generation with Claude CodeS4 Developer Productivity with Claude
Key facts
  • Concrete input/output examples are the most effective way to communicate expected transformations — provide 2–3 worked pairs rather than prose descriptions.
  • Test-driven iteration: write the test suite first, then iterate by sharing specific test failures with Claude.
  • Tests written before implementation should cover expected behavior, edge cases, and performance requirements.
  • The interview pattern has Claude ask you questions to surface design considerations before building.
  • Multiple interacting issues (fixing one affects another) belong in a single detailed message for a holistic fix.
  • Fully independent issues can be handled sequentially in separate iterations.
  • Feedback should be specific: concrete test cases with example input and expected output, not general complaints.

Exam traps

  • Responding to inconsistent output by writing longer, more detailed prose instructions — the graded answer is adding concrete input/output example pairs instead.
  • Feeding interacting bugs to Claude one at a time, so each fix regresses another — interacting issues go in one combined message.
  • Writing the implementation first and bolting tests on afterward when the scenario calls for test-driven iteration — the tests come first, and their failures drive the loop.
  • Vague iteration feedback ("still wrong, try again") offered as an answer choice — specific failures and expected outputs are what make refinement converge.

3.6 CI/CD Integration

Task statement: Integrate Claude Code into CI/CD pipelines

S5 Claude Code for Continuous Integration
Key facts
  • The -p (or --print) flag runs Claude Code in non-interactive mode for automated pipelines; without it, CI jobs hang waiting for terminal input.
  • --output-format json combined with the --json-schema flag enforces structured, machine-parseable output — e.g., structured findings posted as PR comments.
  • CLAUDE.md is the mechanism for providing project context to CI runs; documenting testing standards there improves test generation quality.
  • Session context isolation: the session that generated code is less effective at reviewing its own changes, because it retains the reasoning that produced them.
  • Automated code review should run in a fresh, independent Claude instance, separate from the session that wrote the code.
  • When re-running reviews after new commits, include prior review findings in context so only new issues are reported.
  • Provide existing test files in context so generated tests do not duplicate coverage that already exists.

Exam traps

  • Invented mechanisms: a "headless" environment variable, a --batch flag, or stdin redirection offered instead of -p/--print — those features do not exist; eliminate them on sight.
  • Letting the same session that wrote the code review it — self-review bias means it validates its own reasoning; the graded answer is a fresh independent instance.
  • Parsing Claude's prose output in the pipeline instead of enforcing structure with --output-format json and --json-schema.
  • Re-running reviews from scratch after each commit without prior findings in context, flooding the PR with duplicate reports of already-addressed issues.

60-second recap

  • Team rules and commands live in the repo; user-level files never ship.
  • CLAUDE.md = always-loaded universals; skills = on-demand; path rules = scattered file types.
  • Stated scope decides plan mode vs direct execution.
  • Iterate with examples, tests first, and specific failures.
  • CI: -p, JSON output with a schema, and a fresh reviewer instance.

4.1 Explicit Review Criteria

Task statement: Design prompts with explicit criteria to improve precision and reduce false positives

S5 Claude Code for Continuous Integration
Key facts
  • Explicit criteria beat vague instructions — e.g., "flag comments only when claimed behavior contradicts actual code behavior" is testable; "be careful" is not.
  • General instructions like "be conservative" or "only report high-confidence findings" fail to improve precision compared to specific categorical criteria.
  • High false-positive rates erode developer trust; one noisy category undermines confidence in the accurate ones.
  • Write review criteria that explicitly define which issue categories to report and which to skip.
  • Temporarily disabling high false-positive categories is a recognized remediation to restore developer trust while criteria are rewritten.
  • Define explicit severity criteria with a concrete code example for each severity level.
  • Good criteria are mechanically checkable — e.g., "flag any function exceeding 40 lines," "flag any new third-party dependency."
  • In CI pipelines, fail builds only on explicitly named finding categories, never on vague concerns.

Exam traps

  • Options that add adjectives ("careful," "thorough," "conservative") to fix false positives — the vague-adjective trap; the credited answer is a list of categorical, checkable rules.
  • Confidence thresholds or self-reported confidence scores offered as the precision fix — poorly calibrated and not the root cause.
  • Building a second classifier or filtering model to screen findings — over-engineering when rewriting the criteria fixes the root cause.
  • Leaving a known-noisy category running while "tuning" it — the exam credits temporarily disabling it to restore trust.

4.2 Few-Shot Prompting

Task statement: Apply few-shot prompting to improve output consistency and quality

S5 Claude Code for Continuous IntegrationS6 Structured Data Extraction
Key facts
  • Few-shot examples are the most effective technique for achieving consistently formatted, actionable output.
  • Use roughly 2–4 targeted examples; returns diminish (and can turn negative) beyond about 6.
  • Examples should demonstrate ambiguous-case handling, showing the reasoning, not just the answer.
  • Few-shot examples enable the model to generalize judgment to novel patterns rather than copy the samples.
  • Effective for reducing hallucination in extraction — demonstrate outputting null when the source lacks the information.
  • In review tasks, include examples distinguishing acceptable existing patterns from genuine issues.
  • In extraction tasks, include examples showing correct extraction from documents with varied structures and formats.
  • Examples must show the exact desired output format concretely — demonstrating beats describing.

Exam traps

  • Adjusting temperature to fix inconsistent extraction or formatting — it is a pattern problem, not a sampling problem; the fix is worked examples.
  • Writing longer, more detailed instructions instead of adding examples — prose is re-interpreted each run; examples are not.
  • Example sets containing only easy, obvious cases — without edge and ambiguous cases the model gains no judgment.
  • Treating more examples as strictly better — double-digit example counts over-prompt and can degrade output.

4.3 Structured Output via Tool Use & JSON Schemas

Task statement: Enforce structured output using tool use and JSON schemas

S5 Claude Code for Continuous IntegrationS6 Structured Data Extraction
Key facts
  • Tool use with JSON schemas is the most reliable approach for guaranteed schema-compliant structured output; plain-text JSON requests get conversational preambles and markdown wrapping.
  • tool_choice: "auto" — the model may return plain text; "any" — the model must call some tool; forced — the model must call the named tool.
  • Use "any" to guarantee structured output when the correct schema depends on the input (e.g., unknown document types).
  • Force a specific tool with tool_choice: {"type": "tool", "name": "extract_metadata"} to ensure a particular extraction runs first.
  • Strict schemas via tool use eliminate syntax errors but do not prevent semantic errors (wrong values, sums that do not reconcile).
  • Required fields force fabrication when the source lacks the data — design fields as optional/nullable when documents may not contain them.
  • Extensible enums: include "unclear" for ambiguous cases and "other" plus a free-text detail field for unanticipated categories.
  • Include format normalization rules in the prompt alongside the strict output schema.

Exam traps

  • "Add 'respond only with valid JSON' to the prompt" offered as the most reliable approach — tool use with a schema is the credited answer.
  • Assuming schema enforcement guarantees correct values — semantic errors survive; only syntax errors are eliminated.
  • Marking every field required "for completeness" — required fields on absent data cause fabricated values.
  • Confusing "any" with forced selection — "any" guarantees a tool call but not which tool; only forced selection pins the specific tool.

4.4 Validation, Retry & Feedback Loops

Task statement: Implement validation, retry, and feedback loops for extraction quality

S5 Claude Code for Continuous IntegrationS6 Structured Data Extraction
Key facts
  • Retry-with-error-feedback: on validation failure, append the specific validation errors to the retry prompt rather than rerunning blind.
  • The follow-up request should include the original document, the failed extraction, and the specific errors.
  • With its own failed output and the exact error in context, second-attempt correction rates exceed 90% in practice.
  • Retries are ineffective when the required information is simply absent from the source — no amount of retrying recovers missing data.
  • Persistent retries on missing data waste tokens and can force hallucination; fail gracefully or escalate after one or two attempts.
  • Distinguish semantic validation errors (wrong values, unreconciled sums) from schema syntax errors (already eliminated by tool use).
  • Self-correction schema design: require calculated_total alongside stated_total with a conflict flag so discrepancies self-flag.
  • Adding detected_pattern fields to structured findings enables systematic false-positive analysis and prompt refinement.

Exam traps

  • "Simply retry the request" without appending the validator's specific error — blind retries are a dice roll, not a fix.
  • Retrying repeatedly when the source document lacks the information — the credited answer recognizes retry futility and escalates.
  • Assuming schema-conformant output means correct output — skipping semantic validation because "the schema guarantees it."
  • Reaching for temperature changes or a different model when a validation-feedback loop addresses the root cause.

4.5 Batch Processing Strategies

Task statement: Design efficient batch processing strategies

S5 Claude Code for Continuous IntegrationS6 Structured Data Extraction
Key facts
  • Message Batches API: 50% cost savings, up to a 24-hour processing window, no guaranteed latency SLA.
  • Batch fits non-blocking, latency-tolerant workloads (overnight reports, weekly audits); use the synchronous API for human-blocking tasks.
  • The Batch API does not support multi-turn tool calling within a request — pre-fetch all needed data into the prompt before submission.
  • custom_id fields correlate batch request/response pairs.
  • Handle partial failures by resubmitting only the failed items, identified via custom_id.
  • SLA arithmetic: a 30-hour deadline minus the 24-hour maximum window means submitting every 6 hours.
  • Refine prompts on a small sample via the real-time API before batch-processing the full volume.
  • Route mixed workloads by urgency: latency-tolerant items to batch, urgent items to real-time.

Exam traps

  • Moving human-blocking work (like a pre-merge check) to batch because batch jobs are "usually fast" — without an SLA that is disqualifying.
  • Resubmitting the entire batch after a partial failure instead of isolating failed items by custom_id.
  • Answer options referencing invented features, such as a --batch CLI flag — spotting nonexistent features eliminates the option instantly.
  • Designs assuming the model can call tools mid-request inside a batch — batch is single-turn, fire-and-forget.

4.6 Multi-Instance & Multi-Pass Review

Task statement: Design multi-instance and multi-pass review architectures

S5 Claude Code for Continuous Integration
Key facts
  • A model retains its reasoning context from generation, making it less likely to question its own output — the core self-review limitation.
  • Independent review instances without the prior reasoning context are more effective at catching subtle issues than self-review instructions.
  • In CI, the session that generated code should not review it — use a fresh, separate instance.
  • Multi-pass review: split large reviews into per-file local analysis passes plus a separate cross-file integration pass.
  • The multi-pass split fixes attention dilution, the cause of inconsistent and contradictory findings on large PRs.
  • A larger context window does not fix attention dilution — capacity is not attention quality.
  • Scope the integration pass to cross-file concerns only: data flow and interface boundaries.
  • Verification passes can have the model self-report confidence alongside each finding for downstream routing.

Exam traps

  • "Add an instruction telling the model to review its own output critically" — self-review is structurally biased regardless of prompt wording.
  • Reviewing a large PR in one pass with a bigger context window — more capacity does not restore attention quality; split the passes instead.
  • Consensus voting across repeated review runs — it suppresses the real intermittent catches and is called out as a wrong answer.

60-second recap

  • Checkable criteria beat adjectives; disable a noisy category while you fix it.
  • Two to four examples, including edge and null cases, fix consistency better than temperature.
  • Tool use + schema for structure; nullable fields; semantic checks still needed.
  • Retry with the error appended; stop when the data isn't there.
  • Batch = 50% cheaper, up to 24 h, no SLA, single-turn, custom_id.

5.1 Conversation Context in Long Interactions

Task statement: Manage conversation context to preserve critical information across long interactions

S1 Customer Support Resolution AgentS3 Multi-Agent Research System
Key facts
  • The API is stateless — the complete conversation history must be passed in each subsequent request, and only what you send exists for the model.
  • Progressive summarization condenses numerical values, percentages, dates, and customer-stated expectations into vague summaries; each pass loses precision.
  • Lost in the middle: models reliably process the beginning and end of long inputs but may omit information positioned in the middle.
  • Tool results accumulate in context and consume tokens disproportionately to their relevance; trim them to relevant fields before they enter history.
  • Case-facts block: extract transactional facts into a persistent structured block injected into every prompt, immune to summarization loss and middle-of-context decay.
  • Hybrid preservation pattern: structured extraction of critical data + summarized general discussion + recent exchanges retained verbatim.
  • Place key-findings summaries at the beginning of aggregated inputs; require subagents to include metadata (dates, source locations) in structured outputs.
  • Prompt caching: a cache_control breakpoint caches a reusable prefix for ~5 minutes; reuse pays roughly 1/10 of the input price on the cached portion.
  • Cache stable sections (system prompt, few-shot examples); do not cache the always-changing final user turn.
  • Usable context is smaller than the advertised window: tool definitions and the system prompt consume budget, and attention degrades near the absolute limit.

Exam traps

  • "Summarize the whole conversation" offered as the fix for a forgotten account number or amount — summarization is lossy and silently drops IDs and numbers; the graded answer extracts durable facts into a case block.
  • A pure sliding window that keeps only recent turns — it deletes critical facts stated early (the turn-1 allergy, the original order number).
  • Assuming a bigger context window solves reliability — attention quality does not scale with window size, and documents near the limit still degrade.
  • Options implying the API remembers prior calls — every request must carry its own history.

5.2 Escalation & Ambiguity Resolution

Task statement: Design effective escalation and ambiguity resolution patterns

S1 Customer Support Resolution Agent
Key facts
  • The three canonical escalation triggers: explicit customer request for a human, policy exceptions or gaps, and inability to make meaningful progress.
  • An explicit request for a human is honored immediately; when the issue is within capability but the customer is frustrated, acknowledge the frustration and offer to resolve.
  • Sentiment-based escalation and self-reported confidence scores are unreliable proxies — sentiment does not track complexity, and confidence is poorly calibrated.
  • Poor escalation calibration (escalating easy cases, attempting hard ones) is fixed with explicit escalation criteria plus few-shot examples in the system prompt.
  • When policy is ambiguous or silent on a request, escalate — the agent must not invent policy.
  • Multiple matching customer records require asking for an additional identifier, not heuristic selection.
  • Escalations should carry a structured handoff (customer ID, root cause, amount, attempted steps, recommended action) rather than a raw transcript.
  • Zero records returned from a tool is a valid result, not an error or an automatic escalation trigger.
  • The exam weighs confidently answering something that should have escalated as a worse failure than escalating too eagerly.

Exam traps

  • Options that route escalation through a sentiment analyzer or a self-reported confidence threshold — both are named unreliable proxies; the graded answer is explicit criteria with examples.
  • "Try to resolve it first, then transfer if that fails" when the customer explicitly asked for a human — immediate handoff is the correct behavior.
  • Escalating a frustrated customer whose issue is simple and in-policy — acknowledge and resolve instead.
  • Picking one of several matching records by a heuristic such as most-recent activity — the correct move is asking the customer for another identifier.

5.3 Error Propagation in Multi-Agent Systems

Task statement: Implement error propagation strategies across multi-agent systems

S1 Customer Support Resolution AgentS3 Multi-Agent Research System
Key facts
  • Structured error context — failure type, attempted query, partial results, and alternative approaches — enables intelligent coordinator recovery.
  • Generic error statuses ("operation failed", "search unavailable") hide the context the coordinator needs to choose a recovery path.
  • Silently suppressing errors and terminating the whole workflow on a single failure are both anti-patterns; report the failure in structured form instead.
  • Subagents implement local recovery for transient failures only (e.g., retrying a timeout) and propagate only errors they cannot resolve.
  • Distinguish access failures (timeouts needing retry decisions) from valid empty results — zero matches from a successful search is a result, not an error.
  • Conflating empty results with errors causes endless retries; conflating errors with empty results causes silent data gaps in the final output.
  • Synthesis output should include coverage annotations marking which findings are well supported and where the gaps are.
  • When one subagent fails partway, retry only the failed subagent — successful siblings may have side effects that must not be repeated.

Exam traps

  • A subagent returning a bare "search failed" or empty success — the graded answer always names the four-part structured error context (failure type, what was attempted, partial results, alternatives).
  • Treating zero search results as a failure to retry with new parameters — a valid empty result is not an error.
  • Rerunning every subagent after one fails — the blanket retry repeats side effects; retry only the failed one.
  • Halting the entire workflow (or shipping the report silently incomplete) after a single recoverable subagent failure — proceed with partials and annotate coverage honestly.

5.4 Context in Large Codebase Exploration

Task statement: Manage context effectively in large codebase exploration

S2 Code Generation with Claude CodeS3 Multi-Agent Research System
Key facts
  • Context degradation symptom: in extended sessions the model gives inconsistent answers and references "typical patterns" instead of the actual code it read.
  • Spawn subagents to investigate specific questions so verbose exploration output stays isolated while the main agent preserves coordination context.
  • Subagents start with empty context — summarize key findings from earlier phases and inject the summary into each subagent's initial context.
  • Scratchpad files persist key findings (signatures, mappings, notes) across context boundaries; agents reference them for subsequent questions.
  • Structured state persistence enables crash recovery: each agent exports state to a known location as a manifest the coordinator loads on resume.
  • Use /compact to strip verbose discovery logs and reduce context usage during extended exploration sessions.
  • When prior context is largely stale, a fresh session seeded with a dense structured summary beats resuming a cluttered session — stale tool results cause hallucinated edits.
  • Don't read every file upfront: build understanding incrementally so exploration output doesn't exhaust the window before analysis begins.

Exam traps

  • "Just continue in the same session" (or "use a bigger context window") when the agent has begun answering from generic patterns — the graded fixes are delegation, scratchpads, /compact, or a summary-seeded fresh session.
  • Resuming a stale session after the codebase changed and trusting Friday's file reads — hallucinated line numbers follow; reseed a fresh session instead.
  • Having subagents rediscover the codebase from scratch when the coordinator already holds phase findings — inject a findings summary into their initial context.
  • Keeping all state in-context with no exported manifests, so one crash loses the entire exploration.

5.5 Human Review & Confidence Calibration

Task statement: Design human review workflows and confidence calibration

S6 Structured Data Extraction
Key facts
  • Aggregate accuracy metrics (e.g., 97% overall) can mask poor performance on specific document types or fields; validate by document type and by field before automating.
  • Stratified random sampling of high-confidence extractions measures the true error rate in the lane no human normally reviews.
  • Ongoing sampling of the automated lane is what detects novel confident-hallucination patterns after deployment.
  • Confidence should be output at field level, not only per document — one wrong hard field hides inside an otherwise easy document.
  • Calibrate review thresholds against a labeled validation set; uncalibrated raw scores do not map to known error rates.
  • Route extractions with low model confidence or ambiguous source content to human review.
  • Prioritize scarce reviewer attention on historically low-confidence fields, weak document types, and contradiction cases.

Exam traps

  • "97% accurate, so auto-approve high-confidence extractions and move on" — the aggregate may hide a failing segment; segment-level validation and continued sampling are the graded answer.
  • Reviewing only low-confidence extractions and never auditing the high-confidence stream — errors there are invisible without stratified random sampling.
  • Using a single document-level confidence score (or an arbitrary uncalibrated threshold) for routing — field-level scores calibrated on labeled data are required.
  • Treating the model's self-reported confidence as trustworthy without calibration — it is a proxy that must be measured against known answers first.

5.6 Provenance & Uncertainty in Multi-Source Synthesis

Task statement: Preserve information provenance and handle uncertainty in multi-source synthesis

S3 Multi-Agent Research SystemS6 Structured Data Extraction
Key facts
  • Source attribution is lost during summarization steps when findings are compressed; unstructured hand-offs are where provenance dies.
  • Subagents should output structured claim-source mappings (source URL or document name, relevant excerpt, publication date) that downstream agents must preserve.
  • Conflicting statistics from credible sources are annotated with both values and both attributions — never arbitrarily selected, averaged, or silently dropped.
  • Document analysis should be completed with conflicting values included and explicitly annotated, deferring reconciliation to the coordinator or a human.
  • Reports should structurally separate well-established findings from contested or weakly-supported ones.
  • Publication or data-collection dates are required in structured outputs; temporal differences otherwise get misread as contradictions.
  • A 2021 statistic differing from a 2024 statistic is temporal progression, not a conflict to resolve.
  • Render each content type natively in synthesis output (tables or JSON for data/schemas, prose for narrative, lists for technical findings) instead of uniform flattened prose.

Exam traps

  • "Pick the more credible source" or "use the average" when two credible sources disagree — the graded answer annotates the conflict with both values and attributions.
  • Flagging a contradiction between figures from different years — check dates first; it's likely a trend, and the fix is requiring dates in structured outputs.
  • Passing raw summarized text between agents and expecting citations to survive — only enforced claim-source mapping structures preserve attribution.
  • Presenting contested and well-established findings with equal confidence in one undifferentiated report section.

60-second recap

  • The API is stateless; pin durable facts in a case-facts block.
  • Escalate on explicit request, policy gap, or no progress, never on sentiment.
  • Structured error context up the chain; annotate coverage gaps.
  • Validate by segment; sample the high-confidence lane; calibrate confidence per field.
  • Keep claim–source mappings with dates; report conflicts, don't resolve them silently.
