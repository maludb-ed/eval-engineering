Core of the notes

The 18 trap families

Foundations items usually offer one mechanism-level fix and three plausible distractors. The distractors come from a small set of families. Learn each family's tell and you can strike the option before you finish reading it.

First, the three shapes of a wrong option

The official guide's own answer explanations reject distractors for three recurring reasons. Every trap family below is a specific version of one of them. (Framing from EP12 ▶ 2:00:04 of the CCAR-F course.)

1 · Plausible advice aimed past the cause

A real technique (few-shot examples, a firmer prompt line) that doesn't touch the cause the stem named. Nobody calls it bad. It's beside the point.

Families: T1, T3, T4, T5

2 · The right answer to a question you weren't asked

Good engineering that answers the wrong ask, e.g. consolidating two tools when the stem asked for the most effective first step. Read the last sentence of the stem first.

Families: T16, T17

3 · More machinery than the cause needs

A routing classifier, a trained model, a second reviewer or a bigger context window, when a description change or a stop_reason check removes the cause.

Families: T8, T9, T16, T18

Proportion is the test. When the stem asks for a first step, the cheap fix at the cause wins. When the stem says must / never / always / cannot, only a mechanism wins, because advice can't promise “never”. Note that an absolute inside an option (“tell it never to call the gate”) isn't an absolute in the requirement; it's still advice.

The 18 families

Enforcement: T1–T6 Context & handoffs: T7–T11 Design & configuration: T12–T18
T1

Prompt as guarantee

Enforcement

“Strengthen the system prompt.” “Add MUST in capitals.” “Add few-shot examples of the rule.” “Tell the skill not to write files.”

Why it's wrong
Prompts are probabilistic. Even “works in 99% of test runs” is a non-zero failure rate, and the exam treats that as unacceptable for financial, security or identity rules.
Right-answer pattern
A deterministic control: an Agent SDK hook that intercepts the tool call, a prerequisite gate (e.g. no process_refund until get_customer verifies), forced tool_choice, allowed-tools frontmatter, or business rules in tool code.
Task statements
1.4, 1.5, 2.3, 3.2

Hook: “Guaranteed / required / must never → hook. Preferred / stylistic → prompt.”

T2

Text as control flow

Enforcement

“End the loop when the reply contains ‘task complete’.” “Stop after 15 iterations.” “Treat assistant text as the done signal.” “Have it emit a DONE token.”

Why it's wrong
The model can emit text alongside a tool request, and it can say “finished step one” mid-task. An iteration cap masks bugs instead of controlling the loop.
Right-answer pattern
Drive the loop with stop_reason: tool_use → execute, append the result, call again; end_turn → exit. A cap is only a runaway fail-safe.
Task statements
1.1

Hook: “stop_reason drives the loop; a cap is only a seatbelt.”

T3

Louder, not explicit

Enforcement

“Be careful / thorough / conservative.” “Only report high-confidence findings.” “Write longer, more detailed instructions.” “Still wrong, try again.”

Why it's wrong
Adjectives aren't checkable, and prose gets re-interpreted on every run. Vague feedback doesn't converge.
Right-answer pattern
Categorical, mechanically checkable criteria (what to report and what to skip), 2–4 worked examples including edge cases, and specific failing test cases as feedback.
Task statements
3.5, 4.1, 4.2

Hook: “Criteria you can check beat adjectives you can't.”

T4

Knob, not design

Enforcement

“Lower the temperature to fix inconsistent formatting.” “Raise max_tokens.” “Try a different model” after validation failures.

Why it's wrong
Inconsistent structure is a pattern problem, not a sampling problem. A bigger token budget can't make the model run a tool your loop never executes.
Right-answer pattern
Few-shot examples for format; a validation-feedback retry loop for extraction errors; fix the loop plumbing for loop bugs.
Task statements
1.1, 4.2, 4.4

Hook: “Pattern problems need examples, not sampling tweaks.”

T5

Unreliable proxy

Enforcement

“Escalate when sentiment turns negative.” “Escalate when self-reported confidence < 0.7.” “Route by one document-level confidence score.”

Why it's wrong
Sentiment doesn't track complexity, and self-reported confidence is poorly calibrated. One document score hides a single hard field.
Right-answer pattern
Explicit escalation criteria with few-shot examples. There are three canonical triggers: the customer asks for a human, a policy gap or exception, or no meaningful progress. Use field-level confidence calibrated on labeled data.
Task statements
4.1, 5.2, 5.5

Hook: “Feelings and self-grades aren't routing signals.”

T6

False assurance

Enforcement

“97% accurate overall, so auto-approve.” “It passed the schema, so it's correct.” “Mark every field required for completeness.”

Why it's wrong
An aggregate can hide a failing document type. A schema stops syntax errors, not semantic ones. Required fields for absent data force fabricated values.
Right-answer pattern
Validate by document type and field, stratified sampling of the high-confidence lane, semantic checks (e.g. calculated_total vs stated_total), and nullable fields with unclear/other enum values.
Task statements
1.4, 4.3, 4.4, 5.5

Hook: “Valid isn't correct, and the average isn't every segment.”

T7

Assumed shared memory

Context & handoffs

“The subagent already knows; the coordinator spawned it.” “The API remembers the earlier turn.” “The resumed agent will notice the files changed.”

Why it's wrong
Subagents start with empty context, the Messages API is stateless, and a resumed session trusts its old tool results.
Right-answer pattern
Pass context explicitly in the Task prompt (goals, quality criteria, a findings summary), send the full history on every call, and tell a resumed agent exactly what changed.
Task statements
1.2, 1.3, 1.7, 5.1, 5.4

Hook: “Only what you send exists.”

T8

Bigger window, same attention

Context & handoffs

“Move to a larger context window.” “Review the 40-file PR in one pass.” “Keep everything in one long session.”

Why it's wrong
Attention quality doesn't scale with capacity. Details in the middle get lost, and usable context is smaller than the advertised window.
Right-answer pattern
Per-file passes plus a cross-file integration pass, a case-facts block, subagents and scratchpad files, /compact, and trimming tool results to the fields that matter.
Task statements
4.6, 5.1, 5.4

Hook: “Capacity isn't attention.”

T9

Self-review

Context & handoffs

“Have the session that wrote the code review it.” “Instruct the model to critically review its own output.” “Take a consensus vote across repeated runs.”

Why it's wrong
The generating session keeps the reasoning that produced the code, so it validates itself. Voting suppresses real but intermittent catches.
Right-answer pattern
Use a fresh, independent instance without the generation context, and multi-pass review for large changes.
Task statements
3.6, 4.6

Hook: “A fresh pair of eyes has to actually be fresh.”

T10

Lossy handoff

Context & handoffs

“Summarize the whole conversation.” “Keep a sliding window of recent turns.” “Pass findings on as a prose summary.” “Pick the more credible source” or “average the two figures”.

Why it's wrong
Summaries drop IDs, amounts and dates. Prose loses citations. Choosing or averaging a conflict silently destroys information.
Right-answer pattern
A persistent case-facts block, structured claim–source mappings with dates, conflicts annotated with both values and attributions, and a structured human handoff (customer ID, root cause, amount, recommendation).
Task statements
1.3, 1.4, 5.1, 5.6

Hook: “Structure survives handoffs; prose doesn't.”

T11

Stale context

Context & handoffs

“Resume the old session; the context is valuable.” “Re-run the expensive analysis for each alternative.” “Just keep going in the same session.”

Why it's wrong
Stale file reads produce confident, hallucinated edits, and re-computing a shared baseline wastes the work.
Right-answer pattern
Mostly valid → --resume and name what changed. Largely stale → start a fresh session seeded with a structured summary. Exploring alternatives → fork_session from the shared baseline.
Task statements
1.7, 5.4

Hook: “Resume continues one timeline, fork branches it, and a fresh start plus a summary beats stale context.”

T12

Wrong config scope

Design & configuration

“Put it in ~/.claude/CLAUDE.md.” “Add the server to ~/.claude.json.” “Create the command in ~/.claude/commands/.” “Hardcode the key in .mcp.json.”

Why it's wrong
User-level files never reach version control, so teammates never get them. Committing secrets leaks them.
Right-answer pattern
Project CLAUDE.md, .mcp.json with ${ENV_VAR} expansion, .claude/commands/, .claude/skills/, .claude/rules/ with paths globs. Verify what's loaded with /memory.
Task statements
2.4, 3.1, 3.2, 3.3

Hook: “If teammates need it, it lives in the repo. If it's secret, it lives in the environment.”

T13

Invented feature

Design & configuration

“Set a headless env var.” “Use the --batch flag.” “Pipe the prompt via stdin redirection.” “Let the model call tools mid-batch.” “Edit by line number.”

Why it's wrong
These features don't exist, and the exam plants them as distractors.
Right-answer pattern
-p/--print for non-interactive runs; --output-format json + --json-schema; the Message Batches API is single-turn and keyed by custom_id; Edit matches unique text, not line numbers.
Task statements
2.5, 3.6, 4.5

Hook: “If you've never seen the flag, the exam probably invented it.”

T14

Blind or blanket retry

Design & configuration

“Retry all the subagents.” “Resubmit the whole batch.” “Simply retry the request.” “Keep retrying until the field appears.”

Why it's wrong
Completed siblings may already have committed side effects, and blind retries are dice rolls. Data that isn't in the source can't be retried into existence; pressing for it forces hallucination.
Right-answer pattern
Retry only the failed subagent; resubmit only failed custom_ids; retry with the specific validation errors appended; escalate or fail gracefully after 1–2 attempts when the information is absent.
Task statements
1.2, 4.4, 4.5, 5.3

Hook: “Retry only what failed, include the error, and only if the data exists.”

T15

Error conflation

Design & configuration

“Return ‘operation failed’.” “Zero results is an error, so retry.” “Report the timeout as an empty result.” “Retry the policy violation.” “Halt everything on one failure.”

Why it's wrong
A generic error hides the recovery signal. An empty result isn't an error, and a business-rule error is never retryable.
Right-answer pattern
Structured errors (errorCategory, isRetryable, description) in four classes: transient, validation, business, permission. A tool that ran and failed returns isError; a malformed request is a protocol error. Proceed with partial results plus coverage notes.
Task statements
2.2, 5.3

Hook: “Empty is an answer; an error is a signal. Never confuse them.”

T16

Over-engineering

Design & configuration

“Build a routing classifier for tool selection.” “Add a second model to filter findings.” “Use dynamic decomposition for a known checklist.” “Write a custom MCP server for a mainstream tracker.” “Use SSE for a local server.”

Why it's wrong
It skips the cheap fix at the root cause, and the exam asks for the best first step.
Right-answer pattern
Enrich tool descriptions first, rewrite the criteria, use a fixed pipeline, use the community server, use stdio for local servers, and execute simple fixes directly.
Task statements
1.6, 2.1, 2.4, 3.4, 4.1

Hook: “The best first step is the cheapest fix at the root cause.”

T17

Mismatched strategy

Design & configuration

“Use a fixed pipeline to explore a legacy codebase.” “Start directly and switch to plan mode if it gets hard” (the stem says dozens of files). “Move the pre-merge check to batch.” “Glob to search file contents.”

Why it's wrong
Strategy has to fit the task: known steps or open-ended discovery, contained or cross-cutting, blocking or latency-tolerant, names or contents.
Right-answer pattern
Adaptive decomposition for discovery, plan mode from the start when the scope is stated, the synchronous API for human-blocking work, Grep for contents and Glob for names, and one synthesized reply to multi-issue requests.
Task statements
1.4, 1.6, 2.5, 3.4, 4.5

Hook: “The scope in the stem tells you the mode.”

T18

Tool sprawl

Design & configuration

“Give every subagent the full tool set so it's never blocked.” “One generic do-everything tool.”

Why it's wrong
Eighteen tools degrade selection compared with a focused four or five, and agents misuse tools outside their role.
Right-answer pattern
Scoped tools per role (least privilege), purpose-specific tools with clear contracts, and a narrow cross-role tool for high-frequency needs.
Task statements
2.1, 2.3

Hook: “Four or five focused tools beat eighteen generic ones.”

On exam day: as you read each option, silently label it with a trap number. When three options carry a label, the fourth is your answer. Foundations answers are usually a specific mechanism (a hook, stop_reason, .mcp.json, custom_id, a fresh instance), not an attitude.
