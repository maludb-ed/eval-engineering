Scope

What the course covers, and why it runs wider than ten questions

The domain is worth roughly ten scored items, but its ideas are load-bearing elsewhere on the exam — RAG quality sits in Integration, safety evals in Governance, and results reporting in Lifecycle. M1

Success criteria and metrics

1.5 h

Task statement: define evaluation metrics across accuracy, latency, cost, safety, security.

  • The four properties of good success criteria — specific, measurable, achievable, relevant — applied to LLM systems; why "the agent feels worse" is not a criterion.
  • The five axes as a checklist — credited answers usually name more than one axis; single-axis answers are the trap.
  • Accuracy metric selection: exact match, precision/recall/F1 (and when class imbalance makes F1 lie), ROUGE-L for summarisation, embedding similarity for consistency, rubric scores for open-ended work.
  • pass@k vs pass^k — "one success matters" vs "consistency essential"; identical at k=1, sharply divergent by k=10.
  • Latency: baseline latency vs time to first token; percentiles over means; perceived latency under streaming.
  • Cost per resolved task, not cost per token; amortising cache writes into the unit cost.
  • Safety and security as measured properties: refusal correctness, toxicity rate, PII/PHI leakage, injection resistance, tool-permission violations.
  • Multidimensional targets and criterion-referenced thresholds fixed before the run.

Lab

Three requirement statements — support triage bot, contract-clause extractor, research agent — turned into full criteria tables: axis, metric, target, measurement method, owner.

Traps drilled

Means hide tail latency. Single-axis targets invite regressions on the axis you didn't name. Thresholds set after seeing results aren't criteria.

Quiz: 8 items

M2

Eval datasets and harness design

2 h

Task statement: design evaluation datasets and test frameworks (part 1 of 2).

  • Canonical vocabulary — task, trial, grader, transcript, outcome, evaluation harness, agent scaffold. Distractors work by swapping transcript for outcome.
  • Start small: 20–50 tasks drawn from real failures beats a perfect suite that never gets built; scale toward 50–1,000 as effect sizes shrink.
  • Sourcing: production failures, user reports, dev checks, and deliberate edge cases (irrelevant, oversized, ambiguous, adversarial input).
  • Unambiguous tasks — two domain experts independently reach the same verdict, with a reference solution proving the task is solvable.
  • Balanced sets: negative cases where the behaviour should not fire; class imbalance turns a useless grader into a 95%-scorer.
  • Harness parity with production, clean state per trial — shared state produces correlated failures that look like model regressions.
  • Trials per task and model variance; saturation as a signal to harden the suite.
  • Golden set, regression set, exploratory set — three artefacts, three lifecycles, one named owner.

Lab

Build a 25-task eval set from a support-agent transcript corpus: label, balance, write reference solutions, document the harness contract.

Traps drilled

0% pass@100 on a frontier model means a broken task, not a weak agent. Synthetic-only data misses the distribution that matters. "Add more cases" doesn't fix ambiguous ones.

Quiz: 10 items

M3

Graders and mixed methodologies

2 h

Task statement: design evaluation datasets and test frameworks (part 2 of 2).

  • Three grader families and their economics — code-based (fast, cheap, reproducible, brittle to valid variation), model-based (flexible, non-deterministic, needs calibration), human (gold standard, expensive, the calibration source).
  • Code-based techniques: exact match, unit and integration tests, static analysis, schema validation, tool-call verification, outcome verification against the environment.
  • Model-based techniques: rubric scoring, natural-language assertions, pairwise comparison, reference-based grading, multi-judge consensus.
  • Trajectory vs outcome — grade what was produced, not the path taken; the booking agent whose transcript claims success while no reservation row exists.
  • LLM-judge design: one isolated judge per rubric dimension, an "Unknown" escape hatch, a grading model separate from the generating model, positional and verbosity bias.
  • Calibration: validate against a human-labelled golden set before scaling; 75–90% agreement targets; the "intern test" — if two humans can't agree 80% of the time, the rubric is too vague to automate.
  • The hybrid norm: verifiable rewards ("did it solve the problem?") paired with LLM rubrics ("is it readable, efficient, secure?").
  • Partial credit, grading rigidity, and eval cheating caught by transcript review.

Lab

Write and calibrate an LLM judge: draft a three-dimension rubric, hand-label 30 outputs, measure agreement, revise, re-measure, report the delta.

Traps drilled

The cheapest grader that answers the question wins — "use an LLM judge" is wrong when a unit test settles it. One judge grading five dimensions at once. An uncalibrated judge is evidence of nothing.

Quiz: 10 items · Checkpoint A follows (15 items / 28 min)

M4

A/B testing and iterative improvement

1.5 h

Task statement: conduct A/B testing and iterative improvements.

  • Offline evals gate; online experiments confirm. Neither substitutes for the other.
  • Prompt and config versioning as the precondition for any comparison at all.
  • Regression suites in CI — what blocks a merge versus what only warns.
  • A/B design for LLM systems: unit of randomisation (user, session, or request), sample size and minimum detectable effect, and guardrail metrics that must not move — cost, p95 latency, refusal rate.
  • Why per-request randomisation corrupts multi-turn agent experiments.
  • Shadow mode, canary, staged rollout, champion/challenger — what each proves and what each costs.
  • A shipping sequence to reason with: version → regression → offline eval → A/B significance → canary → rollback path.
  • Closing the loop: every production failure becomes a new eval task.

Lab

Given a +3% eval delta over 40 tasks, design the rollout: justify (or reject) an A/B, choose the randomisation unit, set guardrails and stop conditions, write the rollback trigger.

Traps drilled

A win on a saturated eval is not a win. "Ship it, the eval improved" with no guardrail metrics. Comparing a new prompt against a new dataset.

Quiz: 8 items

M5

Diagnosis and root-cause analysis

2 h

Task statement: diagnose system issues — prompt failure, hallucinations, model mismatch.

  • The domain's core heuristic: trace the symptom to the component that changed.
  • A failure taxonomy with the distinguishing evidence for each — prompt failure, ungrounded generation, retrieval/indexing failure, model mismatch, tool and schema failure, context truncation or compaction loss, agent-loop failure.
  • The canonical scenario: confident-but-wrong RAG answers after a document refresh → investigate retrieval and indexing first, not the prompt, not the model.
  • Splitting RAG metrics — retrieval recall and precision versus generation faithfulness; one end-to-end accuracy number cannot localise a fault.
  • Ablation as method: change one layer at a time against a fixed eval set.
  • Transcript review as a first-class practice rather than a last resort.
  • Hallucination controls — allow uncertainty, ground in quotes, require citations, verification passes — and what each costs.
  • When the answer genuinely is model mismatch: tier escalation and extended thinking as the cheap fix.

Lab

Five annotated failure transcripts — RAG, agent loop, tool schema, prompt, model tier. Diagnose each, name the evidence, propose the minimal fix.

Traps drilled

Swapping models to fix a retrieval bug. Adding "be accurate" to fix hallucination. Rebuilding a pipeline when one component changed.

Quiz: 10 items

M6

Optimising tokens, latency, and cost

2 h

Task statement: optimise token usage, latency, and cost-performance trade-offs.

  • Optimise only once quality is established — the documented order of operations.
  • Model selection and routing: tier by task, Haiku for speed-critical paths, cascades and escalation, per-stage choice inside a pipeline.
  • Caching economics with the real multipliers — writes at 1.25× base input (5-minute TTL) or 2× (1-hour), reads at 0.1×; the break-even read count that justifies a write.
  • Cache mechanics that generate items: model-dependent minimum cacheable prefix, four explicit breakpoints, the tools → system → messages hierarchy, breakpoint on the last stable block, and what invalidates a cache.
  • Context reduction: retrieval trimming, compaction, structured over prose, dropping stale tool output.
  • Output-side levers: max_tokens, sentence and paragraph limits rather than word counts, structured output.
  • Throughput levers: batch processing for non-interactive work, parallel tool calls, streaming for perceived latency.
  • Building a defensible cost model — cost per resolved task across a pipeline, and naming what the optimisation gives up.

Lab

Cost-and-latency teardown of a three-stage pipeline: compute cost per task, apply caching and a tier change, recompute, state the accuracy risk taken.

Traps drilled

Caching a per-request block yields zero hits. Prompts under the model minimum silently don't cache. Downgrading the model before trimming context. Optimising a stage that isn't the cost driver.

Quiz: 10 items · Checkpoint B follows (15 items / 28 min)

M7

Monitoring and observability

1.5 h

Task statement: monitor system performance using logging and observability tools.

  • What a Claude system must emit: full traces carrying prompt version, model, tool calls, token counts, cache hit/miss and stop reason — plus latency percentiles, error and refusal rates, cost per session, escalation rate.
  • Traces as the bridge to evals: the log format should make a failed interaction replayable as a new eval task.
  • Online evals — sampling live traffic into judges, with sampling rates and cost ceilings.
  • Drift: input distribution, retrieval corpus, model version, eval-set staleness — and which signal catches each.
  • Alerting that survives a pager rotation: thresholds on rates and percentiles, never absolute counts, tied to the same guardrails the A/B used.
  • Dashboards by audience — engineer sees traces, architect sees quality and cost trend, executive sees outcome per dollar.
  • Logging and privacy: PII in prompts, retention windows, redaction before storage — the seam with Governance.

Lab

Write the observability plan for a given architecture: event schema, six dashboard metrics, four alerts with thresholds, sampling policy, retention and redaction rules.

Traps drilled

Logging outputs without inputs or versions makes diagnosis impossible. Alerting on absolute counts. Sampling only failures. Monitoring the model but not retrieval.

Quiz: 8 items

M8

Where eval meets the other domains

1 h

Cross-domain reinforcement — no new task statement.

  • Governance: safety evals, red-teaming, human-in-the-loop placement justified by measured error severity, evidence packs for compliance review.
  • Integration: evaluating retrieval and tool layers separately; tool-selection accuracy across MCP servers.
  • Solution design: using eval results to choose between workflow and agentic patterns.
  • Stakeholder communication: reporting results honestly — intervals, blind spots, what the number does not cover — and setting SLAs you can actually measure.
  • Developer enablement: evals in CI and who owns the suite in the team model.

Lab

Write a one-page eval report for an executive sponsor from a supplied results table.
